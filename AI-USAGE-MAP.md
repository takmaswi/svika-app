# AI usage map (paste this to any agent working in the Svika repo)

You are working on Svika. Read this before touching anything AI related. It tells you exactly which AI does what, what is a real model versus a rule, and what the production target is. Do not add AI where a rule or query is enough. Do not overclaim.

## The rule
All inference is server side and deployable to ZCHPC CCE. No model inference on rider phones. Every AI or vendor call goes through an adapter with a mock twin, so providers are swappable and the demo never dies if a vendor is down. No live vendor call sits in the ride path.

## What uses a large language model
Only language understanding. One job: turn a free text Shona or English sentence (for example "Ndoda kuenda Copacabana") into a known stop id from the seeded network. It also writes the bilingual audit narrative for owners.
- Current runtime: Gemini 2.5 Flash, server side (`lib/ai/aiClient.ts`).
- Production target: a self hosted open model (Gemma or Llama class) plus self hosted ASR for voice, fine tuned on our own Shona transport dataset. Gemini is dev time scaffolding only, swapped out through the adapter.
- Honesty line: say "native on server AI is the production target, cloud API in this deployment." Never claim the Shona model is ours while Gemini does the work.

## What is NOT a language model (the real AI value: three spines)
Each spine is a purpose built model measured against a named baseline. Do not replace these with an LLM.
1. ETA prediction. Arrival time with no timetable. Baseline: naive average. This is the headline AI.
2. Commute alerts. Learns a rider's routine and warns before their kombi. Baseline: fixed alarm clock.
3. Revenue anomaly. Flags leakage for owners. Baseline: fixed threshold. Flags patterns, never accuses a named person.

## What is NOT AI at all
- Trip planning: a route query over the seeded network (`lib/trip-planner`). Plain code.
- Destination geocoding (D1): a local index query over a committed corpus of named suburbs, landmarks and roads extracted from the self hosted OSM tiles (`tools/geocode-index`, `apps/web/src/lib/geocode`). Deterministic string scoring, no Google, no vendor in the ride path. Not AI, and the UI never pretends otherwise.
- Alight stop scoring (D1): candidate alight stops near a destination point are ranked by ride minutes plus boarding penalties plus an honest walking tail (`packages/shared/src/plan-to-point.ts`). Documented arithmetic rules; the no service case is stated plainly, never papered over.
- Alight guidance (D1): the in ride "your stop is next" and "chiburuka" cues are the existing geofence trigger engine over vehicle positions, extended to destination trips by the recorded walking tail. Distance thresholds, not a model.
- Kombi trust states (K1): fixed rules over counts from the fare ledger. `public.kombi_board` returns per vehicle aggregates (redeemed fares, distinct fare days, busiest hour load, days above declared seats in a 30 day window) and `apps/web/src/lib/kombi/trust.ts` maps them to unverified, verified or drift with named thresholds. Unverified is the default and today the truthful state of the whole fleet. No model, no score, and the copy names ledger patterns, never a person.
- Rank pulse (V5): how full a kombi is getting at the rank is a COUNT, not a prediction and not a model. The conductor's shift declares which kombi it is on, so every cleared fare carries a vehicle id; `public.kombi_board` (migration 0041) counts the redeemed fares stamped on each vehicle inside a 20 minute window and returns the window with them, and `apps/web/src/lib/kombi/pulse.ts` reads that count against the registry's declared seats with two named thresholds (half the seats is filling, 85 percent is nearly full). The card prints what it counted and over how long, so nothing on it can be read as a departure time. A kombi with no declared seats is counted but not measured, and a count above the declared seats is shown raw rather than clamped: hiding that contradiction would launder a real signal that belongs to the trust rail. Nothing learns here, and nothing would be improved by a model: the ledger already knows the answer.
- Journey recording (M1): capturing a rider's trace is geometry rules with named thresholds, not AI. Accuracy gating, adaptive sampling by speed, a stillness nap for battery and teleport rejection live in `packages/shared/src/journey-trace.ts`; the server stores what the consented rider uploads and computes nothing (migration 0033). Map matching and any analysis of traces are explicitly out of scope for this batch.
- Guide links (M2): walking directions on a shared trip are trace replay, not routing. The recorded points ARE the directions; the viewer's off path, approaching and arrived cues are distance to the polyline with named thresholds and hysteresis, and the step list is derived by Douglas Peucker simplification plus turn and mode segmentation (`packages/shared/src/trace-guide.ts`). Plain geometry, unit tested, and the viewer page says so on screen. No routing engine anywhere; a self hosted Valhalla foot profile is roadmap, slides only.
- Guardian mode trip states (V3): booked, on the kombi, taking longer than usual, arrived safely, ended without a check-in are plain rules over ticket status and timing (`apps/web/src/lib/family/trip-state.ts`): the late flag is status time plus the route's typical duration plus a named 15 minute buffer, nothing learned. Safe arrival is the rider's own tap. If a stall detector ever wants to learn from data, it becomes an AI feature with a baseline and a metrics table first; today it is arithmetic and the copy flags trips, never people.
- Places layer (M3): crowd naming is rules, deliberately not AI. A name is born personal; promotion to suggested needs three independent established authors with a similar name (pg_trgm trigram similarity at a named threshold) inside a 120 m radius (PostGIS), promotion to public needs five distinct authors tapping the suggestion, and shortcuts use the same machinery with a Hausdorff distance bound in metres instead of string similarity (migration 0038, `private.promote_places()`, scheduled by pg_cron every 15 minutes). Recommended naming is one indexed nearest neighbour query. The independence rail (accounts younger than 48 hours do not count) and the report threshold (three distinct reporters hide a name) are counting rules with named constants. Nothing here learns, and every rail flags patterns, never a person.
- Did we get you there right (D2): the explicit channel is three taps into an append only table; the implicit channel compares the planned alight stop and walking tail against a recorded journey trace with geometry rules and named constants (`packages/shared/src/plan-trace-mismatch.ts`: riding speed threshold ends the ride, tolerance radii decide early or late against the plan's reference point, a factor plus dead band decides a long walk; a walk-only or unfinished trace judges nothing). No model. The mismatch table is the honest seed for a future learned ranker, which would then need its baseline and metrics table per the AI law before it ships. No output names a conductor or a vehicle: mismatches belong to plans.
- Remembering and saving trips: database storage.
- Voice: ElevenLabs is a studio tool only. Phrases are generated once and shipped as cached audio. No live call in the ride path.

## The dataset
The Shona to English transport lingo dataset is ours to build, label, and own. It is the moat and the reason native AI becomes viable. Rent the engine now, build the data asset in parallel, drop the dependency once the dataset is big enough to fine tune on.

## One line summary
Gemini 2.5 Flash resolves language today and is replaced by a self hosted fine tuned model in production. The three spines (ETA, commute alerts, anomaly) are the real AI and stay custom. Trip planning, saving trips, and voice are not AI.
